# RGA 阶段性总结材料

## 1. 阶段背景

本项目面向 RK3588 板端的单路相机云台旋转拼接场景。相机输入来自 `/dev/video44`，底层链路以 MIPI CSI、RKISP 和 IMX415 为基础，真实输出格式以 NV12 为主。早期链路可以依靠 OpenCV 和 CPU 先完成采集、预览、保存与拼接闭环，但在板端实时运行时，图像预处理会成为明显压力点。

预处理阶段承担格式转换、旋转、缩放、预览编码和保存前处理等工作。对于 1920x1080 的相机输入，如果全部交给 CPU，会影响预览流畅度，也会压缩后续拼接和关键帧选择的计算余量。因此，本阶段优先选择接入 RK3588 自带的 RGA 图像硬件单元，让它先接管最明确、最适合硬件完成的图像预处理任务。

这一阶段的定位不是重写拼接算法，而是先建立一条可验证、可回退、可持续扩展的板端硬件预处理链路。

## 2. 本阶段目标

本阶段的核心目标是把真实相机帧尽量保持为原始 NV12 数据进入后端，再由 RGA 接管其中一部分预处理工作。具体目标包括：

- 让 `/dev/video44` 的真实 NV12 数据进入后端，而不是在进入 Python 之前就被提前转换为 BGR。
- 建立 `FramePacket(pixel_format="NV12")` 这样的明确数据边界，让后续模块知道当前帧的真实格式。
- 通过 `RgaPreprocessEngine` 调用真实 RGA，而不是只保留一个名义上的加速接口。
- 保留 CPU fallback，保证 RGA 不可用或特定组合不支持时，系统仍可运行。
- 在 preview、save 和 stop 后拼接路径中验证真实相机帧已经进入 RGA。

这个目标强调的是先把硬件加速链路打通并可证明，而不是一次性完成所有图像处理步骤的硬件化。

## 3. 遇到的主要困难

### 3.1 RGA runtime 存在，但不能直接用于开发

板端具备 RGA 运行环境，可以看到 `/dev/rga` 和 `librga.so`，说明硬件和运行时库是存在的。但这并不等于应用层可以直接开发和编译 RGA 调用代码。实际板端缺少开发头文件和 C/C++ 编译器，例如 `im2d.h`、`RgaApi.h` 和 `g++` 等资源并不完整。

这带来的问题是：虽然板端具备运行条件，但无法直接在板端完成 wrapper 编译。必须从 SDK 中寻找匹配的头文件和交叉编译资源，再在 PC 端生成 AArch64 动态库，最后部署到板端验证。

### 3.2 Python 不能方便、稳定地直接调用底层 RGA

底层 `librga.so` 面向 C/C++ 使用，接口涉及 buffer 描述、像素格式、stride、旋转参数、返回状态和硬件约束。若在 Python 中直接复刻这些结构和调用细节，代码会复杂且容易出错，后续维护成本也较高。

因此，本阶段采用一层简化的 C/C++ wrapper。wrapper 负责和 `librga.so`、im2d API 交互，Python 只通过 `ctypes` 调用少量稳定接口。这样可以把复杂的硬件细节限制在 native 层，同时让 Python 后端保持清晰的数据流和状态管理。

### 3.3 相机链路一开始太早转换成 BGR

`/dev/video44` 本身支持 NV12 等 YUV 格式，但旧采集链路中，GStreamer/OpenCV 在 appsink 前通过 `videoconvert` 把图像提前变成 BGR。这样虽然方便 Python 和 OpenCV 处理，却让 RGA 无法在最有价值的位置接管 `NV12 -> BGR` 这一步。

如果进入后端时已经是 BGR，那么即使后端启用了 RGA，也无法证明真实相机的原始 NV12 帧进入了 RGA。这个问题本质上不是 RGA wrapper 能否加载，而是采集边界是否足够靠前。

### 3.4 大分辨率旋转存在 stride 对齐限制

1920x1080 图像旋转 90 度后，目标图像尺寸变为 1080x1920。当前紧密 BGR888 输出的目标宽度 stride 为 1080，但 RGA 对 BGR888 的部分操作要求 width stride 满足 16 对齐。1080 不满足这一要求，而 1088 才满足。

因此，1920x1080 的 90 度或 270 度紧密 BGR888 旋转不能简单地宣称为纯 RGA 完成。若强行追求全 RGA 输出，后续 pipeline 还必须支持 padded stride 图像，或者再做一次紧密化处理。为了保持生产链路稳定，本阶段没有伪装成“全 RGA 旋转”，而是明确采用 RGA 转换、CPU 后旋转的策略。

## 4. 实现路线

### 4.1 先完成后端模块化

为了让硬件加速不是一次性的补丁，本阶段先把后端拆分为相对清晰的模块，包括预处理、几何变换、关键帧选择和拼接引擎等。这样做的原因是：RGA、GPU/OpenCL、NPU/RKNN 对应的是不同阶段的能力，只有先把边界拆清楚，后续才能逐步替换某一段，而不是反复改动整条业务链路。

模块化之后，CPU 版本可以作为稳定 baseline，RGA 版本可以作为可选实现，状态和 benchmark 也能清楚区分当前到底走的是 CPU、RGA fallback，还是实际 RGA。

### 4.2 使用 C/C++ wrapper + Python ctypes

本阶段没有让 Python 直接面对复杂的 RGA 底层接口，而是新增 `libmyui_rga.so` 作为项目内部 wrapper。它对外暴露简化后的图像预处理接口，内部再调用 Rockchip `librga.so` 和 im2d API。

这样设计有三个好处：

- Python 后端只需要处理清晰的输入输出，不需要维护复杂的底层结构体。
- RGA 调用失败时，可以拿到明确错误，并在 Python 层选择是否 fallback。
- 后续如果要扩展 DMABUF、padded stride 或更多格式，可以继续在 native 层演进，而不破坏上层业务接口。

同时，RGA 路径保留 CPU fallback。这样即使硬件调用失败，系统仍能预览、保存和拼接；而在生产验证时，又可以通过 `require_rga` 和状态字段强制区分真实 RGA 与 fallback。

### 4.3 通过交叉编译解决板端开发资源不足

由于板端缺少直接编译 wrapper 所需的头文件和编译器，本阶段从 SDK 中寻找 Rockchip RGA headers 和工具链资源，在 PC 侧生成 AArch64 动态库，再部署到板端。

这条路线比在板端临时补环境更可控，也更符合嵌入式项目的常见交付方式。最终 `libmyui_rga.so` 被部署到板端后，可以被 Python 后端加载，并通过实际样例和真实相机链路验证。

### 4.4 建立真实 NV12 采集路径

旧链路保留为兼容路径，但本阶段新增 raw NV12 采集路径，重点是让真实相机帧以 `FramePacket(pixel_format="NV12")` 的形式进入后端。

一开始使用 `v4l2ctl_nv12_raw` 路线先验证真实 raw NV12 帧和 RGA 的关系，因为它更直接、可控，适合阶段性证明。后续又补充了基于 OpenCV GStreamer raw appsink 的连续采集路径，使 preview 也能使用 raw NV12 进入 RGA。

这样做的关键价值在于：后端不再猜测输入格式，而是明确知道当前帧是 NV12 或 BGR，并据此选择合适的预处理引擎。

### 4.5 采用稳定生产策略

在验证 1920x1080 旋转限制后，本阶段最终没有强行追求“所有步骤都由 RGA 完成”。当前稳定策略是：

- RGA 负责真实相机帧的 `NV12 -> BGR` 转换。
- 对 1920x1080 的 90 度或 270 度旋转，暂由 CPU 在 RGA 转换后完成。
- 状态中明确标记该路径，例如 `convert_only_cpu_rotate` 或 preview 的 `convert_resize_only_cpu_rotate`。

这样既发挥了 RGA 在格式转换和部分缩放上的价值，也避免了 stride 对齐限制导致的不可控失败。更重要的是，系统不会把部分 RGA 路径伪装成完整 RGA 路径。

## 5. 当前成果

本阶段已经完成了从工程接入到板端验证的闭环：

- `libmyui_rga.so` 已成功编译并部署到 RK3588 板端。
- fixed NV12 样例已验证进入 `rga_active`。
- 真实 `/dev/video44` raw NV12 已进入后端，并能构造为 `FramePacket(pixel_format="NV12")`。
- preview 路径已经进入 `rga_active`。
- save 路径已经进入 `rga_active`。
- 手动拍照两张后 stop 拼接已验证通过。
- 当前链路已经能够证明：RGA 不是只在 synthetic benchmark 中生效，而是在真实相机预处理链路中生效。

在预览流畅度方面，后续又将 preview 目标提升到 30fps，并把 preview 路径调整为 RGA 先进行转换和缩放，再由 CPU 对较小的预览图旋转。板端采样显示，后端 preview 处理已经接近 30fps 预算。

## 6. 当前最终路线

当前阶段最终采用的路线是：

```text
/dev/video44 raw NV12
-> FramePacket
-> RgaPreprocessEngine
-> RGA 完成 NV12->BGR
-> CPU 完成必要旋转
-> Preview / Save / Stitch
```

这是当前最稳妥的路线。它能够让 RGA 参与真实相机链路中最适合硬件处理的部分，同时避免 1920x1080 旋转时紧密 BGR888 stride 不对齐带来的不稳定。

这条路线的工程价值在于：既不是停留在 CPU baseline，也不是为了追求“全硬件化”而牺牲稳定性。它保留了清晰的状态标记和 fallback 机制，使后续继续优化时有可靠的基础。

## 7. 当前局限

当前阶段仍有一些明确限制：

- 1920x1080 的 90 度和 270 度不能直接输出紧密 BGR888，原因是目标 stride 对齐限制。
- 全分辨率保存路径中的旋转暂时仍由 CPU 后处理完成。
- preview 虽已采用 RGA 转换和缩放，但小图旋转仍由 CPU 完成。
- GPU/OpenCL 仍未启用，几何变换阶段仍主要依赖 CPU。
- NPU/RKNN 仍未进入真实关键帧选择链路。
- 拼接算法仍主要使用 OpenCV 路线，尚未进入顺序配准、柱面投影和融合优化阶段。
- 当前实现仍是普通内存路径，尚未做 DMABUF 或零拷贝优化。

这些限制并不影响本阶段目标的成立，因为本阶段重点是打通并验证真实相机 NV12 到 RGA 的预处理链路，而不是一次性完成整套图像系统的硬件化。

## 8. 后续工作

后续工作可以按以下方向推进：

1. 整理 CPU、RGA、RGA+CPU 后旋转等不同路径的性能对比数据，为报告提供更清晰的量化依据。
2. 评估是否需要让后续 pipeline 支持 padded stride 图像。如果可以接受 padded BGR 输出，则 1920x1080 的 90 度旋转有机会更多留在 RGA 内完成。
3. 在确认 OpenCL 运行环境和实际收益后，尝试用 GPU/OpenCL 加速几何变换阶段，例如透视变换或重映射。
4. 后续接入 NPU/RKNN，用于关键帧筛选或质量评估，减少无效帧进入拼接流程。
5. 继续优化拼接算法，包括顺序配准、柱面投影、曝光/颜色一致性和融合策略。
6. 在链路稳定后，再评估 DMABUF 或零拷贝方案，减少内存拷贝对实时性的影响。

总体上，本阶段已经完成了 RGA 从“可用接口”到“真实相机链路生效”的转变。后续优化应继续沿着可验证、可回退、逐步替换的工程路线推进。
